1The model is a next-token sampler

Lessons 1–2 · base inference, llama.cpp & quantization

1.1From scores to probabilities

For every position, the network outputs one score — a logit z — per vocabulary token. Softmax turns them into probabilities. A temperature T divides the logits first:

pi = exp(zi / T) / Σj exp(zj / T)

Low T sharpens the distribution toward the top token (greedy decoding as T → 0). High T flattens it, so unlikely tokens get sampled more often. Two filters then cut the tail: top-k keeps the k most likely tokens, and top-p keeps the smallest set whose probabilities add up to p. The survivors are renormalised.

1.2Live: shape the distribution

The logits below are hand-set for three medical prompts. Each candidate token is marked as clinically plausible or wrong. Push the temperature up and watch probability mass leak into the wrong tokens. Then sample 100 times to see how often they come out.

Grey ghost bars are the probabilities before filtering. Entropy measures how spread out the choice is: 2H is the "effective number" of tokens being chosen between.

1.3Why fluent models say wrong things

Nothing in sampling knows what is true. A wrong token with 3% probability will appear roughly 3 times in 100 completions. Because the model then conditions on its own output, one bad token can steer the whole rest of the answer. This is the mechanical root of many hallucinations: it is a probability problem before it is a knowledge problem. For factual medical answers, use low temperature and a tight top-p, and — better — ground the answer in retrieved sources (§5) or tool results (§2).

Lowering T doesn't make the model know more. It only makes it repeat its top guess more consistently. If the top guess is wrong, a confident wrong answer is the result.

1.4Quantization: the same model in a quarter of the memory

A 7-billion-parameter model in 16-bit floats needs 14 GB just for weights. llama.cpp-style quantization stores each weight as a small integer plus one shared scale per block of weights:

q = round(w / s),   s = max|wblock| / (2b−1 − 1),   ŵ = q · s

Smaller blocks adapt the scale to local outliers, so they lose less precision but spend more bits on scales. The weights below are synthetic but realistic: mostly tiny values plus 2% outliers, which is exactly what makes whole-tensor scaling hurt.

Purple lines are the representable levels within each block. Each extra bit adds about 6 dB of SNR. With per-tensor scaling, one outlier stretches the grid for everyone.

2Tools: letting the model do things

Lessons 3, 3A, 4 · LangChain agent, MCP emulation, MCP tools

2.1A tool is a name, a description and a schema

A model cannot look anything up or run any code. What it can do is emit structured text that says "call check_interaction with {"drug_a": "warfarin", "drug_b": "ibuprofen"}". Your code runs the function and feeds the result back. The model decides which tool to call using only the tool's description and its JSON Schema. A vague description is a bug.

Below, four tools sit on top of a small drug and appointment database. The router scores each tool on two things: keyword evidence in the message, and whether the required arguments can be filled. It also scores an "answer directly" option. Type your own message.

When a required argument is missing, the right move is a clarifying question, not a guess. Try "Is it safe to take aspirin together?"

2.2MCP: one protocol for every tool server

The Model Context Protocol standardises the plumbing. A tool server describes itself once. Any MCP-capable host — an IDE, a chat app, an agent framework — can then discover and call its tools over JSON-RPC 2.0. You don't write one integration per app. The diagram replays the exchange for the message you typed above. Click any arrow to inspect the actual message.

Note step 6: the LLM never executes anything. It only proposes a call. Which calls are permitted is the host's decision — that's where you put permissions and audit logs.

3Think → Act → Observe

Lessons 6, 10 · TAO techniques

3.1The loop

One tool call answers one question. Real tasks need several, and each step depends on what the last one returned. The TAO (ReAct-style) pattern makes that explicit. The model writes a short thought, chooses an action, receives an observation, and repeats until it can answer. Everything it has done so far stays in the prompt as a scratchpad.

3.2Live: step through an agent

Each task needs two tool calls against the same database as §2. Turn on the failing tool to see a retry. Lower the iteration cap to see the agent stopped before finishing — a guard every production agent needs.

The bar chart is the prompt size of each LLM call. The scratchpad is re-sent every iteration, so total tokens processed grow roughly quadratically with the number of steps.

Two failure modes to design for. Without an iteration cap, a confused agent can loop until your budget runs out. With a cap and no fallback, it silently returns nothing. Always do both: cap the loop, and on hitting the cap, return partial results with an explanation.

4Memory and guardrails

Lesson 5 · memory & guardrails

4.1The context window is the memory

A chat model is stateless. Between calls it remembers nothing. "Memory" means choosing which past messages to paste back into a prompt of fixed size. Each strategy is a different answer to "what do we drop?":

  • Full buffer: send everything. It's simple, until the history no longer fits.
  • Sliding window: keep the last N messages. It's cheap and predictable, and it forgets old facts.
  • Token budget: keep the newest messages that fit. It uses space better, with the same forgetting.
  • Summary + recent: compress older turns into a summary that keeps key facts. It costs an extra LLM call to write the summary.

4.2Live: what does the model still know?

A 14-message intake conversation. The ★ messages hold key facts: a penicillin allergy, warfarin, and a blood-pressure reading. Choose a strategy and a window size, then ask the final question.

The dangerous case is the quiet one: the allergy was mentioned, then dropped, and the model confidently suggests amoxicillin. Try token budget at 220 tokens, then switch to summary + recent.

4.3Guardrails: check before you send

Whatever enters the prompt may be logged, cached or sent to a third-party API. An input guardrail runs before the model. It redacts personal data, and it routes emergencies away from the model to a human. Regular expressions catch structured identifiers, and checksums cut false positives: the card number below must pass the Luhn check, and the SNILS its control sum. Names are the classic gap. They need an NER model, because regex can't tell "Anna Petrova" from "Aspirin Protect".

Change one digit of the card or SNILS number: it fails the checksum and is no longer treated as an identifier. Remove "chest pain" and routing changes.

5Retrieval: RAG and HyDE

Lessons 8, 13 · RAG techniques, HyDE for clinical guidelines

5.1Search by meaning, measured by angle

Retrieval-augmented generation answers from documents instead of from memory. Every document is turned into a vector, and so is the question. The documents whose vectors point in the most similar direction go into the prompt:

cos(q, d) = q · d / (‖q‖ ‖d‖)

Here the vectors are TF-IDF, so it runs offline. Each dimension is a word, weighted by how rare it is in the corpus. Neural embeddings (as in lesson 13) also match synonyms, but the failure you are about to see — patients and guidelines using different words — hurts both kinds, only less dramatically for neural ones.

5.2HyDE: search with a fake answer

A patient asks about "blood thinners and painkillers". The guideline says "anticoagulation" and "NSAID". Few words overlap, so retrieval misses. Hypothetical Document Embeddings asks the LLM to write an answer first, possibly wrong in its details, and searches with that text. The fake answer is written in guideline vocabulary, so it lands near the real guideline. Only the real documents reach the final prompt; the hypothetical one is discarded.

vHyDE = normalise( (1 − α) · vquery + α · vhypothetical doc )

Pick a preset query to score against hand-labelled relevant documents (✓). The last preset is a two-part question: turn on decompose to retrieve for each part separately.

To run offline, the hypothetical passage here comes from a lookup of concept sentences instead of a live LLM. Left: a 2-D PCA map — it keeps only a small share of the variance, so read distances loosely. Right: the faithful view, each document's similarity to the plain query vs. to the HyDE vector. Points above the diagonal are pulled in by HyDE.

5.3Measure retrieval separately from generation

Recall@k asks: of the documents that should have been found, what share made the top k? MRR (mean reciprocal rank) rewards putting the first relevant document near the top. If the right guideline never reaches the prompt, no amount of prompt engineering fixes the answer. So measure retrieval on its own, before blaming the LLM. Notice too that HyDE is not free: for "my pressure pill makes me cough", plain search already works, and HyDE adds an LLM call for no gain.

6DSPy: compile the prompt, don't hand-tune it

Lesson 9 · DSPy components

6.1Signatures, modules, optimizers

DSPy (Declarative Self-improving Python) replaces hand-written prompt strings with three parts:

  • a signature that states inputs and outputs — patient_message -> intent;
  • a module that decides how to call the LM — dspy.Predict, dspy.ChainOfThought, ...;
  • an optimizer that, given a metric and some labelled examples, chooses instructions and few-shot demos for you.

"Compiling" means running that optimizer. The simplest version, random search over demo sets, is what the figure does. It tries candidate prompts, scores each on a dev set, and keeps the best.

6.2Live: compile an intent classifier

Five intents for a clinic assistant: book, cancel, refill, symptom, results. A pool of 25 labelled messages supplies the demos, 20 more form the dev set, and 15 are held out as the test set. The stand-in "LM" classifies by similarity to each intent's description plus the demos shown for it. It is crude, but it reacts to demos the way a real model does: good examples teach it vocabulary.

The black tick on the bottom bar is the winner's dev score. The gap between it and the blue test bar is the optimiser overfitting a 20-example dev set. Try a few data splits.

6.3What to take away

Demos matter more than wording. Picking them by measurement beats picking them by intuition. And the score you optimised is optimistic by construction. Keep a test set the optimizer never sees, and the larger the search, the larger the dev set you need.

7Teams of agents, and how to grade them

Lessons 6, 7 · multi-agent critic & coordinator, scoring agent answers

7.1Coordinator, specialists, critic

A coordinator splits the request and routes the parts to specialists: a pharmacist agent with drug tools, a scheduler with the calendar, a triage agent with red-flag rules. A critic then grades the merged draft against a rubric and sends it back until every criterion clears the bar, or a round cap is hit. The quality dynamics below are simulated. What's real is the control logic, and the trade-off it creates: each round costs a critique plus a full revision.

Raise the threshold to 0.9: rounds and tokens climb, and sometimes a fix to one criterion knocks another down — a real effect of LLM revisions. Set max rounds to 0 to see the single-agent baseline.

7.2LLM-as-judge: trust, but calibrate

Grading thousands of answers by hand is impossible, so we ask an LLM to score them. Before using a judge, measure it against a sample of human labels. Then pick the pass threshold that maximises agreement. Report Cohen's κ, not raw accuracy: if 55% of answers pass, a judge that always says "pass" already agrees 55% of the time.

κ = (po − pe) / (1 − pe)

Here po is the observed agreement and pe the agreement expected by chance. Then switch on the verbosity bias. LLM judges are known to favour longer answers, and you will see failing-but-long answers sneak over the line.

Simulated labels and scores (seeded). Hollow dots are disagreements; ringed dots are long answers.

7.3"Best agent" is a weighting decision

Lesson 6 benchmarks single, ReAct and multi-agent designs. No design wins on every axis: the critic loop is the most accurate and the safest, and also the slowest and most expensive. Change the weights and watch the ranking flip. Writing the weights down before you see the results is what keeps an evaluation honest.

8Fact-checking with a knowledge graph

Lessons 11–13 · graph verdicts, clinical requirements

8.1Claims are triples

"Lisinopril treats dry cough" becomes (lisinopril, treats, dry cough). An LLM is good at extracting this structure from free text. A knowledge graph is good at checking it, because every edge can be traced to a source. Three outcomes matter:

  • Supported: the same edge exists.
  • Refuted: a contradicting edge exists (causes versus treats, contraindicated versus safe).
  • Not enough info: no edge. This is not "false". A graph only knows what was put in it.

8.2Live: verdicts and message passing

The fill and ring colours show message passing: each round, every node averages its state with its neighbours'. After k rounds, a node "knows" about its k-hop neighbourhood. That is what the graph neural network in lesson 11 does — with learned weights per relation, which is what lets it tell "treats" from "causes".

Try "paracetamol causes bleeding": a 3-hop path exists (paracetamol → pain ← ibuprofen → bleeding), and the subject and object representations grow similar with k. Proximity is association, not evidence — a classic trap for naive graph features.
